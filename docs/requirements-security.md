# Вимоги до безпеки (Фаза аналізу)

## 0. Модель розробки та початковий стан

**Модель розробки: DevSecOps.** Розробка ведеться короткими ітераціями (Agile), а перевірки безпеки вбудовані в кожну з них: вимоги безпеки й модель загроз оновлюються на старті ітерації, SAST виконується автоматично на кожен push і pull request, DAST на кожен push, знахідки оформлюються як задачі в GitHub Issues і закриваються комітами з виправленнями. Модель обрано тому, що проєкт невеликий, змінюється часто і вже має заготовки CI-конвеєра з SAST і DAST.

**Початковий стан (комміт `chore: init security baseline`):**
- застосунок Flask 3.0.3 з ендпоінтами `/`, `/echo`, `/search`, `/login`, `/profile` і базою SQLite (`src/db.py` створює користувачів alice і bob та дві публікації);
- контейнеризація: `Dockerfile`, `docker-compose.yml`;
- CI: `.github/workflows/sast.yml` (Semgrep, Bandit, pip-audit) і `.github/workflows/dast.yml` (OWASP ZAP baseline) з демо-шаблону, ще не перевірені;
- документація безпеки: шаблони вимог, моделі загроз, реєстру ризиків, процесів SAST/DAST і аудиту;
- код містить навмисні вразливості (SQLi, XSS, зберігання паролів відкритим текстом, небезпечна конфігурація) для тренування сканерів.

## 1. Область застосунку

Flask-вебдодаток з аутентифікацією, пошуком і демонстраційною БД (SQLite).

| Елемент | Опис |
|---|---|
| Користувачі | анонімний відвідувач; автентифікований користувач (alice, bob) |
| Ендпоінти | `/` головна; `/echo?msg=` вивід повідомлення; `/search?q=` пошук публікацій; `/login` (GET, POST) вхід; `/profile` профіль (лише після входу) |
| Дані | облікові записи (логін, пароль), публікації, сесійний cookie, `SECRET_KEY` для підпису сесії |
| Середовище | Python 3.11, Flask 3.0.3, SQLite; запуск локально або в Docker; CI на GitHub Actions |

## 2. Функціональні вимоги безпеки

| ID | Вимога | Критерій перевірки | Загроза | OWASP ASVS 4.0.3 |
|---|---|---|---|---|
| **AUTH-1** | Доступ до `/profile` лише для автентифікованого користувача; перевірка на сервері | запит без сесії перенаправляється на `/login` | E, S | V4.1.1 |
| **AUTH-2** | Блокування облікового запису на 5 хв після 5 невдалих спроб входу поспіль | 6-та спроба відхиляється навіть з правильним паролем | S (підбір пароля) | V2.2.1 |
| **STOR-1** | Паролі зберігаються лише як хеш PBKDF2-SHA256 (≥ 600 000 ітерацій) із сіллю; перевірка через порівняння хешів | у БД немає паролів відкритим текстом | I (витік БД) | V2.4.1 |
| **LOG-1** | Кожна спроба входу (успішна, невдала, блокування) журналюється з часом, логіном та IP; паролі не журналюються | записи є в журналі застосунку | R | V7.1.1, V7.2.1 |
| **CONF-1** | `SECRET_KEY` та інші секрети надходять лише з ENV/секретів CI; запасних значень у коді немає; режим debug вимкнено | застосунок не запускається без `SECRET_KEY`; `debug=True` відсутній | I, E | V6.4.1, V14.3.2 |
| **INP-1** | Усі запити до БД параметризовані | у коді немає SQL, зібраного з рядків; Semgrep/Bandit не знаходять SQLi | T, I (SQLi) | V5.3.4 |
| **OUT-1** | Дані користувача виводяться в HTML лише з контекстним екрануванням (шаблони Jinja2) | `/echo` не виконує переданий `<script>` | I, S (XSS) | V5.3.3 |
| **SESS-1** | Сесійний cookie з прапорцями HttpOnly і SameSite=Lax (Secure при HTTPS) | заголовок `Set-Cookie` містить прапорці | S (крадіжка сесії) | V3.4.2, V3.4.3 |
| **HDR-1** | Відповіді містять заголовки безпеки: CSP, X-Frame-Options, X-Content-Type-Options | ZAP baseline не повідомляє про відсутність заголовків | I, T (XSS, clickjacking) | V14.4.3, V14.4.4, V14.4.7 |

## 3. Нефункціональні вимоги

| ID | Вимога | Як виконується |
|---|---|---|
| **NFR-1 Відповідність** | Базові вимоги OWASP ASVS рівня L1 (з окремими пунктами L2) | кожна функціональна вимога прив'язана до пункту ASVS (розділ 2) |
| **NFR-2 Автоматизація перевірок** | SAST на кожен push і pull request, DAST на кожен push | GitHub Actions: `sast.yml`, `dast.yml` |
| **NFR-3 Залежності** | Відомі вразливості залежностей виявляються автоматично (DEP-1) | pip-audit у CI |
| **NFR-4 Експлуатаційність** | Кожна знахідка High/Critical оформлюється як задача з власником і строком | процедура тріажу в `docs/sast-process.md` |
| **NFR-5 Продуктивність тестування** | DAST не повинен перевантажувати сервіс | пасивне сканування ZAP baseline, сканування лише тестового екземпляра |
| **NFR-6 Збереження даних** | Дані зберігаються лише локально в SQLite; файл БД не потрапляє в репозиторій | `*.sqlite3` у `.gitignore` |

## 4. Потенційні загрози

| Загроза | Категорія STRIDE | Ендпоінт / компонент | Наслідок | Вимоги |
|---|---|---|---|---|
| SQL Injection через параметр `q` | Tampering, Information Disclosure | `/search` | читання й зміна будь-яких даних БД, зокрема паролів | INP-1, STOR-1 |
| Reflected XSS через параметр `msg` | Information Disclosure, Spoofing | `/echo` | виконання скрипта в браузері жертви, крадіжка сесії | OUT-1, SESS-1, HDR-1 |
| Підбір пароля, витік паролів | Spoofing | `/login`, БД | захоплення облікового запису | AUTH-2, STOR-1, LOG-1 |
| Підробка сесії через відомий `SECRET_KEY` | Spoofing, Elevation of Privilege | конфігурація | вхід під будь-яким користувачем без пароля | CONF-1 |
| Віддалене виконання коду через debug-режим | Elevation of Privilege | конфігурація | повний контроль над сервером | CONF-1 |
| Розкриття структури БД (показ виконаного SQL) | Information Disclosure | `/search` | полегшує SQLi | INP-1 |
| Clickjacking, MIME-sniffing | Tampering | усі сторінки | обман користувача, виконання контенту | HDR-1 |
| Відсутність аудиту входів | Repudiation | `/login` | неможливо розслідувати атаку | LOG-1 |
| Вразливі бібліотеки | усі | залежності | залежить від уразливості | NFR-3 |

| Ціль | Що захищаємо | Основні вимоги |
|---|---|---|
| **Конфіденційність (C)** | паролі, сесії, `SECRET_KEY`, вміст БД | STOR-1, INP-1, OUT-1, SESS-1, CONF-1 |
| **Цілісність (I)** | вміст БД, результати пошуку, профілі | INP-1, AUTH-1, HDR-1 |

| **Підзвітність** | можливість розслідування інцидентів | LOG-1 |

## 6. Початкові вимоги та ризики

Початкові вимоги безпеки: AUTH-1, AUTH-2, STOR-1, LOG-1, CONF-1. Під час аналізу вимог додано INP-1, OUT-1, SESS-1, HDR-1 і нефункціональні вимоги NFR-1–NFR-6. Під час огляду коду (`src/app.py`, `src/db.py`) виявлено такі передбачувані ризики:

| ID | Ризик | Де | Рівень |
|---|---|---|---|
| R1 | SQL Injection | `/search`: параметр `q` вставляється в SQL через f-string | високий |
| R2 | Reflected XSS | `/echo`: параметр `msg` повертається в HTML без екранування | середній |
| R3 | Слабка автентифікація | `/login`: паролі у БД відкритим текстом, немає обмеження спроб | високий |
| R4 | Вразливі залежності | `requirements.txt`: версії не перевіряються автоматично | середній |
| R5 | Небезпечна конфігурація | запасний `SECRET_KEY` у коді, `debug=True`, у сторінці пошуку показується виконаний SQL | високий |

Детальна оцінка ризиків наведена в `docs/risk-register.csv`, модель загроз у `docs/threat-model.md`.
