# SAST: процес керування

## 1. Інструменти та правила

| Інструмент | Що перевіряє | Конфігурація |
|---|---|---|
| Semgrep | код Python: ін'єкції, XSS, небезпечні налаштування | реєстрові правила `--config auto` і власний набір `.semgrep.yml` |
| Bandit | типові небезпечні конструкції Python | стандартний набір правил |
| pip-audit | відомі вразливості (CVE) у залежностях з `requirements.txt` | база PyPI Advisory / OSV |

**Базовий набір власних правил** (`.semgrep.yml`), орієнтований на очевидні помилки цього проєкту:

| Правило | Що виявляє | Рівень | CWE |
|---|---|---|---|
| `sql-injection-fstring` | SQL, зібраний з f-string, конкатенації або `format()` | ERROR | CWE-89 |
| `flask-reflected-xss-fstring` | повернення параметра запиту в HTML через f-string | ERROR | CWE-79 |
| `plaintext-password-comparison` | пряме порівняння пароля з полем БД | ERROR | CWE-256 |
| `hardcoded-secret-key-fallback` | `SECRET_KEY` із запасним значенням у коді | WARNING | CWE-798 |
| `flask-debug-enabled` | `app.run(debug=True)` | WARNING | CWE-489 |

## 2. Запуск у конвеєрі

1. Workflow `.github/workflows/sast.yml` запускається на кожен push і pull request.
2. Semgrep, Bandit і pip-audit формують звіти `semgrep.sarif`, `bandit.sarif`, `pip-audit.json`. Збій інструмента не зупиняє інші кроки.
3. Звіти SARIF завантажуються у вкладку **Security → Code scanning** (анотації в коді й у pull request), усі три звіти також зберігаються як артефакт `sast-reports`.
4. **Security gate:** останній крок запускає власні правила з параметром `--error`. Якщо знайдено хоча б одну проблему, збірка позначається як невдала, і pull request не слід зливати.

Локально ті самі перевірки запускаються командами `make semgrep`, `make bandit`, `make audit`.

## 3. Керування звітами (тріаж)

1. **Збір.** Після кожного запуску Security Champion переглядає Code scanning і артефакт `sast-reports`.
2. **Дедуплікація.** Знахідки різних інструментів, що вказують на ту саму проблему (наприклад, SQLi від Semgrep і Bandit B608), об'єднуються в одну задачу.
3. **Перевірка.** Кожна знахідка перевіряється вручну. Хибне спрацювання закривається в Code scanning зі статусом *False positive* і коментарем, чому.
4. **Пріоритезація.** Критичність визначається за рівнем сканера, експлуатованістю (чи доступна точка ззовні без автентифікації) і впливом на активи:

| Критичність | Приклад | Строк виправлення |
|---|---|---|
| Critical | SQLi без автентифікації, паролі відкритим текстом | 2 дні |
| High | XSS, відомий `SECRET_KEY`, debug-режим | 7 днів |
| Medium | відсутні заголовки безпеки, CSRF | 30 днів |
| Low / Info | розкриття версії сервера | наступний реліз |

## 4. Формування задач

- Для кожної підтвердженої знахідки рівня Medium і вище створюється задача в **GitHub Issues** за шаблоном *Security finding* (`.github/ISSUE_TEMPLATE/security-finding.md`).
- Назва: `[SEC][<Severity>] <проблема> in <місце>`, мітка `security`.
- У задачі вказуються джерело (правило сканера), файл і рядок, опис, критичність з CWE, пов'язаний ризик (`R1–R5`) і вимога, рекомендоване виправлення, критерій закриття і строк.
- Задача призначається відповідальному розробнику.

## 5. Відстеження і закриття

1. Виправлення робиться в окремій гілці; коміт містить посилання на задачу (`Closes #N`).
2. Pull request проходить SAST; security gate має бути зеленим, а знахідка зникнути з Code scanning.
3. Після злиття pull request GitHub автоматично закриває задачу, а сповіщення Code scanning переходить у стан *Fixed*.
4. Статус ризику в `docs/risk-register.csv` оновлюється на `Closed`, а підсумки фіксуються в `docs/audit-report.md`.
5. Відкриті задачі з міткою `security` переглядаються на кожній ітерації; прострочені за SLA ескалюються власнику продукту.
