**Об'єкт:** вебзастосунок `pr1-2` (Flask, SQLite), репозиторій https://github.com/vastorozhenko/pr1-2
**Дата:** 12.11.2026
**Модель SDLC:** DevSecOps
**Методика:**
- перевірка виконання вимог із `docs/requirements-security.md`;
- огляд змін у коді (pull requests #8 і #10);
- порівняння результатів SAST/DAST до і після виправлень;
- ручна перевірка сценаріїв атак із `docs/threat-model.md`.

## Перегляд змін у коді

Усі виправлення внесено через pull request #8 з гілки `security-fixes`. Перед злиттям pull request пройшов 5 перевірок: SAST (push і pull_request), DAST і Code scanning для Semgrep і Bandit. Кожен коміт виправляє одну задачу і закриває її ключовим словом `Closes #N`.

| Коміт | Зміна | Файли |
|---|---|---|
| `947fdf7` | параметризований запит у `/search`, прибрано показ SQL | `src/app.py`, `search.html` |
| `476741a` | вивід `/echo` через шаблон із екрануванням | `src/app.py`, `echo.html` |
| `43f63ab` | хеші PBKDF2, блокування входу, журнал аудиту | `src/app.py`, `src/db.py` |
| `1cd574f` | `SECRET_KEY` лише з ENV, debug вимкнено, прапорці cookie | `src/app.py`, `Dockerfile`, `docker-compose.yml` |
| `d8980ac` | CSRF-токен у формі входу | `src/app.py`, `login.html` |
| `ad3e5b7` | заголовки безпеки | `src/app.py` |
| `36f35dd` | Flask 3.0.3 → 3.1.3 | `requirements.txt` |
| PR #10 | контейнер запускається від непривілейованого користувача `appuser`, БД в іменованому томі | `Dockerfile`, `docker-compose.yml` |

Під час підсумкового аудиту у вкладці Code scanning виявлено ще одну знахідку Semgrep: `dockerfile.security.missing-user` (рівень Error, `Dockerfile:8`), контейнер запускався від root. Правило почало спрацьовувати після того, як на етапі DAST було виправлено синтаксично невірний `CMD`, і Semgrep зміг розібрати Dockerfile. Знахідку оформлено як задачу #9 і виправлено окремим pull request #10, тобто вона пройшла той самий цикл: тріаж, задача, виправлення, перевірка в CI, закриття.

**Хибне спрацювання.** Правило `django-no-csrf-token` після виправлення продовжує вказувати на `login.html`: воно шукає Django-тег `{% csrf_token %}`, а застосунок на Flask використовує власний токен. Перевірка вручну підтвердила захист (POST без токена повертає 400), тому алерт відхилено в Code scanning зі статусом *False positive* і коментарем, як передбачає `docs/sast-process.md`.

**Залишкові ризики:**
- **R7:** дії CI підключено за тегом (Low), ризик прийнято;
- **розкриття версії сервера розробки** (Low), ризик прийнято;
- **прапорець Secure для cookie** вимагає HTTPS;
- **блокування за іменем користувача:** атакувальник може навмисно заблокувати чужий обліковий запис на 5 хв, а лічильники зберігаються в пам'яті й скидаються під час перезапуску;
- **немає політики складності паролів:** демонстраційні паролі слабкі, хоч і зберігаються як хеші.

## Ролі та відповідальність

У навчальному проєкті всі ролі виконувала одна особа, але кожен етап закріплено за роллю. Така сегрегація обов'язків має діяти в реальній команді.

| Роль | Обов'язки в інтеграції безпеки |
|---|---|
| **Owner (власник продукту)** | затверджує вимоги безпеки і рівень прийнятного ризику; приймає рішення про прийняття залишкових ризиків (R7, заголовок Server); контролює дотримання SLA |
| **Security Champion** | веде модель загроз і реєстр ризиків; підтримує правила SAST (`.semgrep.yml`); проводить тріаж звітів SAST/DAST, відсіює хибні спрацювання, створює задачі; проводить підсумковий аудит |
| **Dev (розробник)** | реалізує вимоги безпеки; виправляє вразливості в окремих гілках з посиланням на задачу; не зливає власні зміни без зеленого security gate і рев'ю |
| **QA (тестувальник)** | виконує DAST і ручні перевірки сценаріїв атак; підтверджує виправлення повторним тестуванням перед закриттям задачі |
| **DevOps** | підтримує конвеєр CI (SAST, DAST, pip-audit, Code scanning); керує секретами (`SECRET_KEY` у секретах/ENV); оновлює залежності й образи |

**Матриця RACI** (R відповідає, A затверджує, C консультує, I інформується):

| Етап | Owner | Security Champion | Dev | QA | DevOps |
|---|---|---|---|---|---|
| Вимоги безпеки | A | R | C | C | I |
| Модель загроз і ризики | A | R | C | C | C |
| Налаштування SAST/DAST у CI | I | C | I | C | R/A |
| Тріаж знахідок, задачі | I | R/A | C | C | I |
| Виправлення | I | C | R | C | I |
| Перевірка виправлень | I | A | C | R | I |
| Прийняття залишкового ризику | A | R | I | I | C |
| Підсумковий аудит | A | R | C | C | C |

**Сегрегація обов'язків:**
- автор зміни не затверджує її сам: потрібні зелений security gate і рев'ю іншого учасника;
- рішення про прийняття ризику приймає Owner, а не розробник;
- доступ до секретів має лише DevOps.

## Рекомендації

Рекомендації враховують невеликий розмір проєкту і модель DevSecOps: пріоритет мають автоматичні перевірки в конвеєрі, а не важкі ручні процедури.

**Процес і конвеєр (найближча ітерація):**
1. Увімкнути захист гілки `main`: злиття лише через pull request з обов'язковими перевірками (SAST security gate) і щонайменше одним рев'ю. Це закріпить сегрегацію обов'язків технічно.
2. Підключати дії GitHub Actions за SHA (закриття R7) і ввімкнути Dependabot для дій і залежностей Python.
3. Увімкнути Secret scanning з push protection і CodeQL як другий SAST-рушій.
4. Додати сканування Dockerfile та образу (Trivy або Hadolint).
5. Запускати активне сканування ZAP (`zap-full-scan`) за розкладом на тестовому стенді, бо baseline є лише пасивним.

**Застосунок:**
6. Розгортати застосунок через gunicorn за nginx з TLS: тоді можна ввімкнути `COOKIE_SECURE=1` і HSTS, а заголовок версії сервера приховується.
7. Додати політику паролів (мінімум 12 символів, перевірка на поширені паролі) і зберігати лічильники блокування в постійному сховищі (Redis/БД). Обмежувати спроби також за IP, щоб зменшити ризик навмисного блокування чужих облікових записів.
8. Передавати журнал аудиту в централізовану систему моніторингу з правилами тривог на серії `login_failed` і `csrf_rejected`.

**Організація:**
9. Переглядати модель загроз і реєстр ризиків на початку кожної ітерації та після кожної суттєвої зміни архітектури.
10. Проводити для команди коротке навчання OWASP Top 10 і розбір реальних знахідок цього проєкту. Security Champion має щокварталу переглядати власні правила Semgrep.
