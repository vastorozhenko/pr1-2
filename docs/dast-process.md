# DAST: процес тестування

## 1. Процедура

1. Запустити застосунок: локально `sudo make up` (Docker Compose, http://127.0.0.1:5000) або в CI (workflow `dast.yml` запускає застосунок на раннері).
2. Запустити ZAP baseline scan: локально `sudo make zap` (образ `ghcr.io/zaproxy/zaproxy:stable`, мережа хоста), у CI дія `zaproxy/action-baseline@v0.14.0` на кожен push.
3. Зберегти звіт: локально `reports/zap/zap.html` і `zap.xml` (каталог `reports/` не потрапляє в репозиторій), у CI артефакт `zap-report`.
4. Провести тріаж за процедурою з `docs/sast-process.md`: зіставити алерти з наявними задачами, підтвердити або позначити хибні, створити задачі для нових проблем рівня Medium і вище.
5. Після виправлень повторити сканування і порівняти результати.

**Обмеження baseline-сканування.** ZAP baseline виконує павука (spider) і **пасивний** аналіз відповідей, атакувальних запитів він не надсилає. Тому SQLi і XSS цей режим не підтверджує, і вони додатково перевірені вручну запитами до працюючого застосунку (`/search?q=' UNION SELECT ...` повертає логіни й паролі, `/echo?msg=<script>...` повертає скрипт без змін). Для повного динамічного тестування рекомендовано активне сканування (`zap-full-scan.py`) на тестовому стенді.

**Висновки:**
- Високих ризиків baseline не виявив. Основні знахідки стосуються відсутніх заголовків безпеки (HDR-1) і захисту форм.
- Два алерти підтверджують проблеми, знайдені SAST: відсутність CSRF-токена (#5) і показ SQL на сторінці пошуку (#4). Тобто SAST і DAST доповнюють одне одного.
- Для відсутніх заголовків створено задачу #6. Розкриття версії сервера прийнято як залишковий ризик: у промисловому середовищі застосунок має працювати за зворотним проксі (nginx), який приховує цей заголовок.

**Перевірка залежностей (pip-audit):** знайдено вразливість PYSEC-2026-2151 (CVE-2026-27205, CVSS 4.3 Medium) у Flask 3.0.3: за деяких способів звернення до сесії Flask не додає заголовок `Vary: Cookie`, тому кеш-проксі може зберегти відповідь з даними користувача. Виправлено у Flask 3.1.3. Створено задачу #7.
